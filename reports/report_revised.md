# Уведомление о расходах по карте — исправленная редакция требований

Подготовлено агентом SoloHive по результатам проверки и ответов на уточняющие вопросы (11 из 11). Исходный файл: `requirements.pdf`.

Плейсхолдеры [уточнить: …] — вопросы, на которые ещё нет ответа.

## Изменённые требования

### REQ-01 (Часть A › Цели)

**Было:** Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.

**Стало:** Цель: дать держателю карты возможность оперативно узнать о достижении личного бюджета расходов за календарный месяц при проведении (клиринге) покупки.

*Устраняет: D-01*

### REQ-03 (Часть A › Дизайн процесса UI)

**Было:** Карты → Расходы → Уведомления. На экране видны переключатель, поле «Порог, ₸», сумма за
месяц и кнопка «Сохранить». При ошибке ввода сообщение появляется под полем.

**Стало:** Экран мобильного приложения (Карты → Расходы → Уведомления) отображает переключатель включения услуги (enabled), поле ввода «Порог, ₸», сумму проведённых расходов за текущий месяц (в тенге) и кнопку «Сохранить». Если текущие расходы уже превышают введённый порог, под полем выводится предупреждение: «Расходы за месяц уже превышают порог — уведомление придёт в следующем месяце». При получении ошибок валидации поле подсвечивается текстом из ответа API (RFC 7807 detail). Для заблокированных, закрытых карт и карт не в KZT экран настроек блокируется с информационным сообщением.

### REQ-04 (Часть A › Требования к изменениям › BPMN схема процесса)

**Было:** Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка
push → завершение.

**Стало:** BPMN схема процесса: вычитывание события проведения операции из Kafka → проверка дубликата по operationId → пересчёт накопленных расходов месяца покупки (Asia/Almaty) → проверка условий отправки push (enabled=true, расходы >= порог, push в текущем месяце ранее не отправлялся) → отправка запроса в push-шлюз → фиксация статуса отправки в БД → завершение.

### Ф-1 (Часть A › Требования к изменениям › Функциональные требования)

**Было:** Ф-1. Держатель активной карты KZT задаёт целый порог от 1 000 до 1 000 000 ₸
включительно. По умолчанию уведомление выключено.

**Стало:** Ф-1. Держатель активной карты в валюте KZT может включить сервис уведомлений и задать целочисленный порог расходов от 1 000 до 1 000 000 ₸ включительно. По умолчанию уведомление выключено (enabled = false). При перевыпуске карты порог, статус enabled, сумма расходов текущего месяца и статус отправки push автоматически переносятся на новую карту.

### Ф-2 (Часть A › Требования к изменениям › Функциональные требования)

**Было:** Ф-2. Месяц определяется по дате совершения покупки в Алматы. В расходы входят
проведённые покупки. Возврат уменьшает расходы месяца исходной покупки. Переводы
и снятие наличных исключаются.

**Стало:** Ф-2. Календарный месяц определяется по дате и времени совершения покупки в часовом поясе Asia/Almaty (UTC+5). В расходы включаются только операции с подтверждённым проведением (клирингом). Операция возврата (REFUND) уменьшает сумму накопленных расходов того календарного месяца, к которому относится исходная покупка (originalOperationId), и не изменяет расходы текущего месяца. Переводы и операции снятия наличных в расчёте расходов не учитываются.

### Ф-3 (Часть A › Требования к изменениям › Функциональные требования)

**Было:** Ф-3. Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше,
клиент получает push. На карту приходится максимум один такой push за календарный
месяц.

**Стало:** Ф-3. Если накопленные расходы месяца переходят от значения ниже порога к значению, равному порогу или превышающему его, сервис формирует push-уведомление клиенту при условии enabled = true. На одну карту формируется не более одного push-уведомления за календарный месяц. Последующие операции возврата, уменьшающие сумму расходов ниже порога, не сбрасывают признак отправки push за текущий месяц.

### Ф-4 (Часть A › Требования к изменениям › Функциональные требования)

**Было:** Ф-4. При изменении порога накопленная сумма сохраняется. Если она ниже нового
порога, следующее достижение вызывает push независимо от истории предыдущей
настройки.

**Стало:** Ф-4. При изменении порога накопленные расходы текущего месяца сохраняются. Если накопленная сумма строго ниже нового порога, его последующее достижение вызывает push независимо от того, отправлялось ли уведомление при старом пороге. Если накопленная сумма равна новому порогу или превышает его, push в текущем месяце не отправляется.

*Устраняет: D-35*

### НФТ-1 (Часть A › Нефункциональные требования)

**Было:** Сервис передаёт push на отправку в течение минуты после получения события.

**Стало:** НФТ-1. Сервис расходов передаёт запрос на отправку push в сервис уведомлений не более чем через 60 секунд после вычитывания события клиринга из брокера сообщений для не менее чем 99% событий (перцентиль p99) при входящем потоке до 300 событий в секунду.

*Устраняет: D-20*

### REQ-11 (Часть A › Требования к данным)

**Было:** Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах,
признак отправки и порог в тенге.

**Стало:** Требования к данным: в БД хранятся cardId (UUID), месяц расчёта (ГГГГ-ММ, Asia/Almaty), operationId (UUID, первичный ключ дедупликации), сумма операции в тиынах (bigint), порог расходов в тенге (integer), признак активности enabled (boolean), признак факта отправки push в месяце pushSent (boolean).

### REQ-12 (Часть A › Требования к интеграции)

**Было:** Приложение читает и сохраняет настройки через дочерний документ «Уведомление о
расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет
исходный итог.

**Стало:** Требования к интеграции: интеграция с процессингом осуществляется асинхронно через топик Kafka card-clearing-events. Обработка событий идемпотентна: при повторном получении события с существующим operationId пересчёт расходов и повторная отправка push не производятся.

### REQ-14 (Часть A › Критерии приемки)

**Было:** Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Февральский счётчик вырос на 4 000 ₸

**Стало:** Критерий приемки №2: покупка совершена 31 января в 23:58 по времени Asia/Almaty на 4 000 ₸, проведена клирингом 1 февраля в 00:03 по времени Asia/Almaty. Ожидаемый результат: увеличивается счётчик расходов за январь на 4 000 ₸; счётчик расходов за февраль не изменяется.

### REQ-16 (Часть B › Общие параметры)

**Было:** | Description | Сохранение порога. Функциональные требования: чтение порога |
| REST type | GET |
| Authorization | Bearer, сессия владельца карты |
| Controller | AlertsController |
| URL type | Dev / Prod |
| Request URL | Dev: /alerts/saveLimit . Prod: — |

**Стало:** Сохранение настроек порога: PUT /api/v1/cards/{cardId}/alert-limit. Авторизация: Bearer-токен владельца карты. Content-Type: application/json. Тело запроса: {"amount": integer, "enabled": boolean}. Валидация: amount — целое число от 1000 до 1000000 включительно.

### Логика работы метода п. 4 (Часть B › Логика работы метода)

**Было:** 4. Заменить настройку и вернуть результат сохранения.

**Стало:** Успешный ответ сохранения настроек: HTTP 200 OK, Content-Type: application/json. Тело ответа: {"amount": 50000, "enabled": true}.

### Логика работы метода п. 5 (Часть B › Логика работы метода)

**Было:** 5. При отклонении суммы вернуть прежнее состояние и результат ERROR.

**Стало:** Обработка ошибок параметров сохранения: при невалидной сумме порога возвращается HTTP 400 Bad Request, Content-Type: application/problem+json. Пример тела: {"code": "AMOUNT_OUT_OF_RANGE", "field": "amount", "detail": "Порог должен быть целым числом от 1 000 до 1 000 000 ₸"}.

### REQ-34 (Часть B › Статусы › 403. Unsuccessful — Forbidden)

**Было:** 403. Ответ в случае, если на указанный ресурс доступ запрещен. 500. Ответ в случае, если произошла внутренняя ошибка сервера. #### 400. Unsuccessful — Bad request {"message":"Некорректный запрос"} #### 401. Unsuccessful — Unauthorized {"message":"Требуется вход"} #### 403. Unsuccessful — Forbidden Для чужой карты возвращается 404, как и для отсутствующей карты. ##### 404 {"message":"Карта не найдена"}

**Стало:** Ошибки статуса карты и авторизации: для карты другого клиента или отсутствующей карты возвращается HTTP 404 Not Found {"message": "Карта не найдена"}. Для неактивной карты клиента (заблокирована/закрыта) возвращается HTTP 422 Unprocessable Entity {"code": "CARD_NOT_ACTIVE", "detail": "Карта заблокирована или закрыта"}. Для карты в валюте, отличной от KZT, возвращается HTTP 422 {"code": "CARD_CURRENCY_NOT_SUPPORTED", "detail": "Настройка доступна только для карт в KZT"}.

## Новые требования

- **Ф-5** (Часть B. REST API): Чтение настроек порога: GET /api/v1/cards/{cardId}/alert-limit. Авторизация: Bearer-токен владельца карты. При успешном выполнении возвращает HTTP 200 OK с телом {"amount": integer, "enabled": boolean, "spentThisMonth": integer}, где spentThisMonth — сумма проведённых расходов карты за текущий календарный месяц в тенге (округлённая вниз). Если карта отсутствует или принадлежит другому клиенту — HTTP 404 Not Found. *(устраняет: D-05)*
- **Ф-6** (Функциональные требования): Интеграция с сервисом push: при наступлении условий отправки push сервис расходов передаёт в push-шлюз объект {"cardLast4": string, "spentMonthKzt": integer, "thresholdKzt": integer, "language": "RU"|"KZ"}. Текст для локали RU: «Расходы по карте •• {cardLast4} за месяц достигли {spentMonthKzt} ₸ — это ваш порог {thresholdKzt} ₸». Текст для локали KZ формируется по утверждённому банковскому шаблону.
- **И-1** (Требования к интеграции): Спецификация события клиринга процессинга (Kafka-топик card-clearing-events, партиционирование по cardId): {"operationId": "UUID", "cardId": "UUID", "cardLast4": "string(4)", "operationType": "PURCHASE"|"REFUND", "amountTiyn": integer, "purchaseDateTime": "YYYY-MM-DDThh:mm:ss+05:00", "originalOperationId": "UUID" (nullable)}.
